半导体 Etch 多智能体框架初版方案文档

1. 背景与目标

本方案面向半导体 Etch 工艺场景，目标是构建一个采用 主 Agent + 多 Subagent 的多智能体系统，用于支持 Etch recipe 参数分析、机理解释、文献类比、历史数据建模、多目标优化、DOE 实验设计与结果汇总。

当前各部分实现成熟度不一致，因此第一版方案不追求端到端完全自动化，而是优先建立：

1. 可扩展的多智能体框架；
2. 每个 subagent 的职责边界；
3. 当前有 API 或工具支持时的接入方式；
4. 当前暂无实现支持时的占位逻辑、基础文档和 mock 工具；
5. 最后通过一个 Etch Skill 将所有 subagent 串联起来。

整体设计参考 OpenCode 的 subagent 机制：

* Tool 负责确定性、原子化能力，例如 API 调用、文件解析、DOE 矩阵生成、模型预测请求等；
* Subagent 负责多步推理、任务拆解、专家判断和结果解释；
* Skill 负责把一组 subagent 和工具封装为完整工作流。

3. 推荐工作流

3.1 主流程

Step 1: 用户输入 Etch 场景问题
  - 目标：改善条纹度 / CD / 畸变率 / profile / selectivity 等
  - 输入：layer 类型、当前 RCP、历史数据、约束、实验预算
Step 2: Orchestrator 解析任务
  - 判断用户问题属于：
    A. 参数解释
    B. 参数优化
    C. DOE 设计
    D. 文献调研
    E. 机理边界分析
    F. 综合方案生成
Step 3: 并行或顺序调用 subagent
  - Mechanism Agent 给出机理约束与方向解释
  - Literature Agent 给出类似场景参考
  - Data Agent 给出历史数据驱动推荐
  - DOE Agent 给出实验设计方案
  - Constraint Agent 检查安全边界、工艺边界、RCP 合规性
Step 4: Integration Agent 融合结果
  - 判断不同 agent 之间是否冲突
  - 区分“数据支持强”“机理支持强”“文献支持弱”“仅探索建议”
  - 给出推荐优先级
Step 5: Report Agent 生成最终文档
  - 推荐 RCP 调整方向
  - Top N 候选方案
  - DOE 计划
  - 风险点
  - 后续实现和调试任务

3.2 推荐编排模式

第一版建议采用 Supervisor + Expert Pool + Producer-Reviewer 混合模式。

Etch Orchestrator
  ├── 并行调用：Literature / Mechanism / Data
  ├── 顺序调用：Constraint 检查 Data 推荐结果
  ├── 根据缺口调用 DOE 生成验证实验
  ├── Integration 做冲突仲裁
  └── Report 输出最终文档

这样可以避免单一 agent 同时承担过多职责，也便于后续替换真实 API 或仿真工具。

4. 各 Subagent 详细设计

4.1 Etch Orchestrator 主控 Agent

定位

Etch Orchestrator 是用户直接交互的主控 agent，负责理解用户目标、拆解任务、选择 subagent、融合结果，并决定是否需要继续追问用户。

输入

* 用户问题；
* 当前 RCP 参数；
* layer 类型，例如 LCH / MCH；
* 工艺目标，例如 Row1/Row7 条纹度、畸变率、CD 约束；
* 历史数据文件；
* 是否允许使用文献 API、数据 API、DOE 工具、仿真工具。

输出

* 任务拆解结果；
* 被调用 subagent 列表；
* 各 agent 输出摘要；
* 最终建议方案。

4.2 Mechanism Agent：机理模型 / 仿真 Agent

当前状态

当前仿真 owner 尚未提供具体实现支持，因此第一版不应假设已有真实仿真能力。建议先把 Mechanism Agent 设计为 机理逻辑占位 + 输入输出协议定义 + mock simulator 工具。

主要职责

1. 接收 RCP 参数；
2. 给出基于物理/化学常识的方向性解释；
3. 建立 RCP 参数与 Etch 性能指标之间的概念映射；
4. 输出工艺窗口边界、偏差根因假设；
5. 为 Data Agent / DOE Agent 提供约束条件；
6. 等真实仿真 API 接入后，替换 mock 工具。

不建议第一版承担的任务

* 不直接给出“确定最优 recipe”；
* 不伪造仿真数值；
* 不把机理解释当作实际实验结论；
* 不替代历史数据模型或 DOE 统计分析。

# Etch Mechanism Assumptions
## 1. Scope
This document defines first-version qualitative assumptions for Etch mechanism reasoning before the real simulator is integrated.
## 2. Supported Reasoning
The mechanism agent may reason about:
- plasma power impact,
- pressure impact,
- gas flow ratio impact,
- bias-related ion energy impact,
- selectivity and profile tendency,
- CD bias risk,
- microloading or pattern dependency hypothesis.
## 3. Unsupported Reasoning
The mechanism agent must not:
- generate fabricated simulation values,
- claim exact CD or etch rate prediction,
- claim validated process windows without data,
- override experimental or historical data results.
## 4. Output Confidence
Every conclusion should be labeled as:
- HIGH: supported by known mechanism and user-provided data,
- MEDIUM: mechanism-plausible but not experimentally verified,
- LOW: hypothesis only.

推荐 Tool：文献 API Adapter

文件：.opencode/tools/etch-literature-api.ts

import { tool } from "@opencode-ai/plugin"
const BASE_URL = process.env.ETCH_LITERATURE_API_BASE || "http://10.18.220.244:32300"
async function sleep(ms: number) {
  return new Promise(resolve => setTimeout(resolve, ms))
}
export default tool({
  description: "Call the Etch literature knowledge-base API. Use this to create a conversation, send a streaming literature query, wait, and retrieve citation metadata. If the API is unavailable, return a structured error.",
  args: {
    query: tool.schema.string().describe("Literature search question for Etch process, mechanism, DOE, or optimization methods"),
    waitMs: tool.schema.number().default(5000).describe("Wait time before retrieving message info"),
  },
  async execute(args) {
    try {
      const convResp = await fetch(`${BASE_URL}/create_conversation`, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({})
      })
      if (!convResp.ok) {
        return JSON.stringify({
          success: false,
          stage: "create_conversation",
          status: convResp.status,
          error: await convResp.text(),
          fallback: "Use placeholder literature query plan."
        }, null, 2)
      }
      const conv = await convResp.json()
      const conversationId = conv.conversation_id || conv.id
      const chatResp = await fetch(`${BASE_URL}/chat_query_v2_sse`, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          conversation_id: conversationId,
          query: args.query
        })
      })
      if (!chatResp.ok) {
        return JSON.stringify({
          success: false,
          stage: "chat_query_v2_sse",
          status: chatResp.status,
          error: await chatResp.text(),
          conversationId
        }, null, 2)
      }
      await sleep(args.waitMs)
      const infoResp = await fetch(`${BASE_URL}/get_message_info?conversation_id=${encodeURIComponent(conversationId)}`, {
        method: "GET"
      })
      if (!infoResp.ok) {
        return JSON.stringify({
          success: false,
          stage: "get_message_info",
          status: infoResp.status,
          error: await infoResp.text(),
          conversationId
        }, null, 2)
      }
      const info = await infoResp.json()
      return JSON.stringify({
        success: true,
        conversationId,
        messageInfo: info
      }, null, 2)
    } catch (error) {
      return JSON.stringify({
        success: false,
        error: error instanceof Error ? error.message : String(error),
        fallback: "Literature API unavailable. Use query strategy and placeholder citation schema only."
      }, null, 2)
    }
  },
})

推荐 Tool：数据 API Adapter

文件：.opencode/tools/etch-data-api.ts

import { tool } from "@opencode-ai/plugin"
const BASE_URL_1 = process.env.ETCH_DATA_API_BASE || "http://10.20.52.249:5314"
const BASE_URL_2 = process.env.ETCH_DATA_API_BASE_ALT || "http://10.20.52.249:5315"
export default tool({
  description: "Call the Etch data prediction and multi-objective optimization API. Use this for historical data quality report, model comparison, NSGA-II optimization, and user parameter override prediction.",
  args: {
    action: tool.schema.enum([
      "health_check",
      "data_quality",
      "model_compare",
      "optimize",
      "predict_override",
      "export_files"
    ]).describe("API action to perform"),
    layerType: tool.schema.enum(["LCH", "MCH"]).describe("Etch layer type"),
    payloadJson: tool.schema.string().default("{}").describe("Action-specific JSON payload"),
    base: tool.schema.enum(["primary", "secondary"]).default("primary").describe("Which API base URL to use"),
  },
  async execute(args) {
    const baseUrl = args.base === "primary" ? BASE_URL_1 : BASE_URL_2
    let payload: any
    try {
      payload = JSON.parse(args.payloadJson)
    } catch {
      return JSON.stringify({
        success: false,
        error: "Invalid payloadJson. Please provide valid JSON."
      }, null, 2)
    }
    try {
      const response = await fetch(`${baseUrl}/${args.action}`, {
        method: args.action === "health_check" ? "GET" : "POST",
        headers: { "Content-Type": "application/json" },
        body: args.action === "health_check"
          ? undefined
          : JSON.stringify({
              layer_type: args.layerType,
              ...payload
            })
      })
      if (!response.ok) {
        return JSON.stringify({
          success: false,
          baseUrl,
          action: args.action,
          status: response.status,
          error: await response.text(),
          fallback: "Data API unavailable. Return schema-level plan only."
        }, null, 2)
      }
      const data = await response.json()
      return JSON.stringify({
        success: true,
        baseUrl,
        action: args.action,
        result: data
      }, null, 2)
    } catch (error) {
      return JSON.stringify({
        success: false,
        baseUrl,
        action: args.action,
        error: error instanceof Error ? error.message : String(error),
        fallback: "Data API unavailable. Use fallback data plan and do not fabricate metrics."
      }, null, 2)
    }
  },
})

数据 API 调试与配置方案

当数据 API 恢复后，建议按以下顺序调试：

1. health_check
   - 确认 5314 / 5315 哪个服务可用
   - 记录版本号、模型版本、数据更新时间
2. data_quality
   - 检查 LCH / MCH 数据源是否能正确选择
   - 对比样本数、特征数、排除列是否合理
3. model_compare
   - 确认 6 种模型均有返回
   - 检查 R² 是否区分 train / validation / time-series CV
4. optimize
   - 检查目标函数方向是否正确：
     - minimize Row1 stripe
     - minimize Row7 stripe
     - maximize Row7 distortion rate
     - maximize distortion ratio
   - 检查约束：
     - Bias CD
     - Bottom CD
     - Max CD
5. predict_override
   - 用户只输入部分参数时，确认其余参数是否自动填充
   - 分类变量原始字符串是否被正确编码
6. export_files
   - 检查推荐参数、summary、trials、PCA、model comparison 文件是否可下载

import { tool } from "@opencode-ai/plugin"
import path from "path"
export default tool({
  description: "Generate and analyze generic DOE designs for Etch experiments. Supports coded design matrix generation and delegates analysis/reporting to Python.",
  args: {
    action: tool.schema.enum([
      "generate_full_factorial",
      "generate_fractional_factorial",
      "generate_taguchi_placeholder",
      "generate_response_surface_placeholder",
      "analyze_results"
    ]).describe("DOE action"),
    factorCount: tool.schema.number().min(1).max(12).describe("Number of experimental factors"),
    levelsJson: tool.schema.string().default("{}").describe("JSON definition of levels for each factor"),
    resultsCsvPath: tool.schema.string().optional().describe("Path to completed DOE results CSV for analysis"),
    outputDir: tool.schema.string().default("outputs/doe").describe("Output directory"),
  },
  async execute(args, context) {
    const script = path.join(context.worktree, ".opencode/tools/etch_doe.py")
    const cmd = [
      "python3",
      script,
      "--action", args.action,
      "--factor-count", String(args.factorCount),
      "--levels-json", JSON.stringify(args.levelsJson),
      "--output-dir", args.outputDir
    ]
    if (args.resultsCsvPath) {
      cmd.push("--results-csv-path", args.resultsCsvPath)
    }
    try {
      const result = await Bun.$`${cmd}`.text()
      return result.trim()
    } catch (error) {
      return JSON.stringify({
        success: false,
        error: error instanceof Error ? error.message : String(error),
        suggestion: "Check whether Python dependencies are installed and paths are valid."
      }, null, 2)
    }

4.6 Constraint Agent：工艺约束 / Recipe Guardian Agent

为什么需要新增

Etch 场景中，仅有数据优化或 DOE 设计是不够的。即使 Data Agent 给出某组参数更优，也必须检查：

* 是否超出历史参数空间；
* 是否违反设备安全边界；
* 是否违反工艺窗口；
* 是否违反 Bias CD / Bottom CD / Max CD 约束；
* 是否存在不合理参数组合；
* 是否与机理解释冲突。

因此建议新增 Constraint Agent，作为所有推荐方案的“守门员”。

3. 检查设备约束；
4. 检查历史空间外推风险；
5. 检查机理冲突；
6. 输出 PASS / FAIL / WARNING；
7. 为 Integration Agent 提供可行性标签。

4.7 Integration Agent：方案融合 / 冲突仲裁 Agent

为什么需要新增

多个 agent 的输出可能冲突，例如：

* Data Agent 推荐增大某参数；
* Mechanism Agent 认为增大会带来 profile 风险；
* Literature Agent 给出的类似场景不完全匹配；
* DOE Agent 建议先做局部探索；
* Constraint Agent 标记某些候选为 WARNING。

因此需要 Integration Agent 做统一仲裁。

核心职责

1. 汇总所有 subagent 输出；
2. 判断证据强弱；
3. 处理冲突；
4. 给出推荐优先级；
5. 明确哪些建议可直接实验，哪些只能作为假设；
6. 输出下一步实验计划。

推荐证据分级

Level A: 历史数据 + 约束检查 + 机理解释一致
Level B: 历史数据支持，但机理或约束存在 WARNING
Level C: 机理或文献支持，但缺少数据验证
Level D: 仅 DOE 探索建议
Level E: 信息不足，不建议执行

12. 第一版最小可用系统定义

第一版不要求所有 API 可用。只要满足以下条件，就可以认为框架已经初步可用：

1. Etch Orchestrator 能根据用户目标拆解任务。
2. 7 个 subagent 的职责边界清晰。
3. API 不可用时不会伪造结果。
4. DOE Agent 能生成通用编码矩阵。
5. Constraint Agent 能输出 PASS / WARNING / FAIL / UNKNOWN。
6. Integration Agent 能融合多源结果并标注证据等级。
7. Report Agent 能生成完整 Markdown 报告。
8. 后续真实 API 或仿真工具可以无缝替换 mock tool。

13. 总结建议

第一版重点不是让每个 subagent 都“很聪明”，而是先保证系统结构正确、边界清晰、输出可信。

推荐优先级如下：

优先级 1：Etch Orchestrator + Skill 框架
优先级 2：DOE Agent 本地工具
优先级 3：Constraint Agent 规则框架
优先级 4：Data API Adapter
优先级 5：Literature API Adapter
优先级 6：Mechanism Simulator Adapter
优先级 7：Integration + Report 强化

这套设计的核心原则是：

Tool 做确定性执行；
Subagent 做专家推理；
Skill 做流程编排；
Constraint Agent 做安全边界；
Integration Agent 做证据仲裁；
Report Agent 做可交付输出。

你这版场景最关键的优化点是：不要让数据、机理、文献、DOE 直接互相覆盖结论，而是让它们都输出“证据片段”，再由 etch-integration 统一做证据分级和冲突仲裁。这样即使当前 API 都不成熟，也能先把流程跑起来，并且后续接入真实工具时不用推倒重做。
