# 教学演讲稿

这份讲稿按 60 分钟设计。讲师可以照读，也可以把每段压缩成自己的口语表达。方括号中的内容是现场动作提示，不需要读出来。

## 0-5 min：开场与心智模型

大家好，今天这节课我们不讲“怎么写一个神奇 prompt”，也不把 OpenCode 当成更聪明的自动补全工具。

今天的主线是：如何把一个业务场景，沉淀成一个可复用、可验证、可交接的 Agent 应用。

先给一个定义：Agent 不是一个模型，而是一个带状态的决策循环。它至少包含目标、状态、动作空间、观察空间、决策策略和运行时。放到软件开发里，就是它能读文件、搜代码、调用脚本、看测试结果、再根据观察继续修正。

所以我们今天反复看的不是“模型回答得多漂亮”，而是四件事：

1. 动作空间有没有被设计清楚。
2. 证据、验证和纠偏有没有闭环。
3. context 有没有分层外部化，而不是堆进一个 prompt。
4. 权限、工具、脚本、数据边界和人工 review 有没有一起设计。

[打开 `agent_jc/demo/all_demo/README.md`]

这个教学包里有四个 demo：规则文档生成、文档规范迁移、PDF 复现项目生成、权限沙箱和受控数据服务。它们对应的不是四个复杂业务系统，而是四种常见业务场景的最小可复用骨架。

## 5-8 min：OpenCode 项目骨架

[打开 `lesson_guides/context分层速查表.md`]

先看这个分层表。一个稳定的 Agent 应用，不应该只有当前聊天里的 prompt。

对话层负责说明这一次要做什么；规则层放在 `AGENTS.md`；流程层放在 Skill；入口层是 Command；动作层是 Tool、脚本或 Data Service；证据层是文档、样例、schema 和 golden cases；观察层是测试结果和 manifest；安全层是权限、白名单和 stop rules。

这套结构的价值是：当用户下一次提出类似需求时，Agent 不需要重新发明流程，而是复用已有 context。

[打开 `lesson_guides/OpenCode项目骨架讲解.md`]

今天每个 demo 我们都按同一个问题看：

第一，业务一句话是什么？
第二，如果只靠 prompt，会不稳定在哪里？
第三，我们把 context 拆成哪些层？
第四，Agent 可以做什么，不能做什么？
第五，哪个脚本执行，哪个脚本验证？
第六，哪些结果能自动验证，哪些必须人工 review？

## 8-20 min：Demo 00 规则驱动 Dashboard

[进入 `00_rule_dashboard_agent`]

第一个 demo 是入门场景：讲师只说一句话，Agent 生成教学进度 dashboard。

业务场景很普通，类似周报、项目进度、培训状态同步。用户不会每次给完整 JSON，通常只会说“Demo 0 讲完了，Demo 1 进行中，后面还没开始”。如果每次让模型临时写 HTML，字段、样式、状态口径都会漂移。

[打开 `README.md` 和 `AGENTS.md`]

这里的做法是把规则沉淀下来。`AGENTS.md` 规定输出位置、禁止改模板、必须运行验证。Skill 规定字段怎么抽取，Command 提供 `/dashboard` 入口，脚本负责渲染，验证脚本负责检查必要区块。

[打开 `.opencode/skills/dashboard-generator/SKILL.md`]

注意 Skill 不是业务知识大全，它是这个任务的 SOP：加载什么 context、调用什么脚本、怎么验证、什么时候停止。

[展示 prompt]

```text
/dashboard 当前培训总时长 60 分钟。Demo 0 已完成，Demo 1 进行中，Demo 2 和 Demo 3 未开始。用户刚问：如何把一个临时 prompt 沉淀成稳定 Agent 应用？请生成讲师 dashboard。
```

[运行]

```bash
python3 run_demo.py
```

[打开 `output/dashboard.html`、`output/status_report.md`、`output/dashboard_manifest.json`]

这里要强调：我们不是只看 HTML 长得像不像。manifest 记录了输入、输出、生成时间和验证提示。状态报告说明哪些内容来自模板，哪些需要讲师确认。

Demo 00 的 takeaway 是：规则驱动文档生成的重点，不是让模型写得更花，而是把模板、字段、脚本和验证固化下来。

## 20-33 min：Demo 01 文档规范与跨语言迁移

[进入 `01_doc_spec_portability`]

第二个 demo 是基于历史文档和样例的开发。场景是把 Python 订单折扣规则迁移成 JS 风格模块。

这个 demo 对应很多真实业务：比如 A 平台测试程序迁移到 B 平台，或者老系统规则迁移到新系统。它不是单纯翻译语法，而是要同时看功能文档、源代码、目标语言样例、迁移规范和 golden tests。

[打开以下文件]

```text
docs/order_discount_spec.md
docs/porting_spec_py_to_js.md
references/source/python_order_rules.py
references/examples/js_reference_style.mjs
tests/golden_cases.json
```

这里可以提醒学员：这些文件不是越多越好，而是分工明确。功能文档说明语言无关的业务规则；源代码是历史实现；目标样例告诉 Agent 目标风格；golden cases 是验收标准。

[展示 prompt]

```text
/port-spec 请把 references/source/python_order_rules.py 按 docs/porting_spec_py_to_js.md 的规范迁移到 generated/pricing.mjs。先输出迁移计划和风险点，再调用脚本生成，并运行 golden tests。
```

[运行]

```bash
python3 run_demo.py
```

[指出输出]

```text
Golden cases passed: 5
Port validation passed.
```

[打开 `generated/pricing.mjs`、`output/migration_report.md`、`output/validation_manifest.json`]

现在 golden cases 覆盖 5 条：3 条正常路径，2 条错误路径。这里的教学点是：迁移开发不能只验证 happy path，错误处理也应该被纳入验收。

但我们也不能过度声称。自动验证通过只说明这 5 条样例行为一致，不说明金额精度策略生产可用，也不说明所有优惠券组合都被覆盖。金额计算、业务优先级和平台差异仍然需要 owner review。

Demo 01 的 takeaway 是：基于历史文档的开发，关键是先定义验收证据，再让 Agent 生成候选实现。

## 33-48 min：Demo 02 PDF 抽取与复现项目生成

[进入 `02_pdf_reproduction_agent`]

第三个 demo 是从 PDF 或论文里抽取实验逻辑，再结合本地环境包生成最小复现项目。

很多人会把这类任务理解成“让 AI 读 PDF，然后给我建议”。但这里我们要演示的是更工程化的流程：先抽取 evidence，再生成设计摘要，再生成代码，再验证。

[打开]

```text
references/pdf_extraction_rules.md
papers/synthetic_agent_eval_paper_text.md
env_pkg/chip_eval_env.py
```

PDF 抽取规则规定要提取哪些字段：目标、环境要求、算法步骤、默认参数、实验逻辑、原生代码指令和限制。这样 Agent 不是读完后凭印象写代码，而是先生成结构化证据。

[展示 prompt]

```text
/reproduce-paper 请从 papers/synthetic_agent_eval_paper.pdf 提取实验逻辑，结合 env_pkg/ 中的本地环境库，生成一个最小可运行复现项目。不要声称复现了论文全部结论，只验证语法和示例测试。
```

[运行]

```bash
python3 run_demo.py
```

[打开]

```text
output/evidence.json
output/design_brief.md
repro_project/src/adaptive_window.py
repro_project/tests/test_adaptive_window.py
output/validation_manifest.json
```

这里有一个很重要的表达边界：验证脚本通过，只能说生成项目语法正确、样例测试通过。不能说论文已经被完整复现，更不能说算法科学结论成立。

这正是 Agent 应用里的人机协同点：Agent 可以完成证据抽取和最小项目生成，但公式语义、实验口径、真实数据适配，仍需要人审。

Demo 02 的 takeaway 是：辅助编程不只是“读资料给建议”，也可以完成一部分执行动作；但执行动作必须被 evidence 和验证约束。

## 48-56 min：Demo 03 权限沙箱与受控数据服务

[进入 `03_permission_sandbox_agent`]

第四个 demo 是安全边界。它有两个场景：一个是 sandbox 配置变更，一个是 lot history 的 QTime / UT 查询。

先看配置变更。用户要求打开 `beta_dashboard` flag，但 Agent 不能改 production 配置，只能生成 proposal，并应用到 sandbox 输出。

[打开 `opencode.json`]

这里要强调：Skill 里写“不要做”只是软约束，`opencode.json` 和脚本/API 才是运行时边界。这个配置禁止编辑 `protected/**`，并禁止读取敏感原始数据。

[展示 prompt]

```text
/safe-change 请把 sandbox 中的 beta_dashboard flag 打开，原因是培训演示需要。不要读取 customer_data.csv，不要修改 protected/prod_config.json，只能通过受控脚本生成 proposal 并应用到 sandbox。
```

第二个场景更贴近数据分析工程师：查询 lot history 的 QTime / UT 汇总。真实业务里，Agent 不应该直接连数据库，也不应该读原始客户数据。它应该通过 Data Service 获取脱敏、聚合、可审计的结果。

[打开]

```text
policy/data_access_policy.json
schemas/lot_query_schema.json
scripts/query_lot_history_service.py
scripts/validate_data_service.py
```

这里的本地 Python 脚本是在模拟 Data Service。真实落地时，可以替换成带鉴权、审计、限流和字段脱敏的 HTTP API。

[展示 prompt]

```text
/query-lot 请查询 LOT-A12 的 QTime / UT 汇总并生成图。不要读取 protected/lot_history_raw.csv，只能通过数据服务脚本返回聚合结果。
```

[运行]

```bash
python3 run_demo.py
```

[指出输出]

```text
Config patch validation passed.
Data service validation passed.
```

[打开]

```text
output/proposal_001.json
output/lot_history_summary.json
output/lot_qtime_chart.svg
output/data_service_manifest.json
```

验证脚本检查了字段白名单、lot 白名单、审计日志和 protected 文件 hash。也就是说，它证明了这个 demo 没有直接泄露原始字段，敏感文件没有被改动。

但仍然要说明：QTime / UT 的业务口径是否正确，需要数据 owner 和工艺 owner 确认。自动验证不能替代业务审批。

Demo 03 的 takeaway 是：生产里的 Agent 不是权限全开的自动化脚本，而是被封装在受控动作空间里的协作者。

## 56-60 min：总结

[打开 `lesson_guides/context分层速查表.md`]

最后回到今天的四个方法论。

第一，先设计动作空间，再谈自治。没有工具约束、权限边界和验证回路，Agent 只是放大不稳定性。

第二，先让 Agent 学会取证、验证和纠偏，再要求它自动完成任务。Demo 01 和 Demo 02 都是在先定义证据和验收标准，再生成代码。

第三，不要把 context 当成越来越大的 prompt，要把它当成可分层、可外部化、可交接的系统。AGENTS.md、Skill、Command、Tool、references、output manifest 各有位置。

第四，真正让 Agent 在生产里站住脚的，不是某一个神奇 prompt，而是运行时、记忆、协议、工具、安全和工作流一起配合。

如果大家回去要做自己的业务 demo，可以从这四个问题开始：

1. 用户的一句话需求是什么？
2. Agent 能做哪些动作，不能做哪些动作？
3. 证据、模板、schema、样例和测试分别放在哪里？
4. 最终输出如何验证，哪些地方必须人工 review？

这就是今天这套 OpenCode context engineering demo kit 想传达的核心。
