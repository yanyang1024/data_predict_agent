这是一份专为研发工程师编写的**大模型智能体（Agent）Skill 设计与开发全景指南**。

在 LLM 走向生产环境的今天，传统的“面向过程/对象编程”正在向“面向意图与 Agent 编程”演进。本文将从底层认知、架构设计、上下文工程到工程实践，为你彻底讲透如何在 Agent 应用（如 OpenCode 等）中设计、开发和迭代一个高质量的 **Skill（技能）**。

# 工程师的 Agent 进阶指南：如何设计与沉淀一个优秀的 Skill？

## 1. 重新定义：什么是智能体应用与 Skill？

### 1.1 什么是智能体应用（Agent Application）？
智能体应用不再仅仅是一个“一问一答”的对话框，或者一套写死的 UI。它是**一种以自然语言为交互界面，能够理解用户意图，自主规划并调用工具链完成业务场景，同时还能根据特定用户需求进行灵活“数据后处理”的新型软件形态。**
* **对话式入口：** 极大地降低了用户操作复杂系统的门槛。
* **目标导向：** 关注于“完成某个应用场景”（如排查线上 OOM、自动生成 API 文档等）。
* **灵活后处理：** 传统应用输出固定报表，智能体应用可以在获取底层数据后，根据用户的临时追问（“帮我把这些错误按时间线汇总成表格，并翻译成中文”）进行零代码的即时处理。

### 1.2 什么是 Skill（技能）？
在智能体架构中，**Skill 是对资源和操作流程的抽象，它使用自然语言将底层 API、系统资源逻辑整合起来，专门针对某个具体业务场景提供解决方案。**
你可以将它理解为 Agent 时代的“微服务”。它告诉大模型：**在遇到某类特定问题时，你应该扮演什么角色，按什么套路思考，以及可以使用哪些工具。**

---

## 2. Skill 与现有工程概念的区别

为了打破原有思维惯性，我们需要厘清 Skill 与现有概念的区别：

### 2.1 Skill vs 传统脚本 / 应用服务
* **传统脚本/服务（Deterministic）：** 强类型的入参、固定的执行路径（`if/else/for`）、确定的输出。一旦遇到未捕获的异常或非预期输入，直接 Crash。
* **Skill（Probabilistic & Resilient）：** **模糊输入，结构化输出。** Skill 赋予了代码“常识”和“容错性”。当调用的底层 API 报错时，Skill 能够通过大模型的理解能力阅读报错信息，自我修正参数并重试，而不是直接抛出 500 错误。

### 2.2 Skill vs Workflow（工作流）
* **Workflow（如 Zapier, CI/CD, n8n）：** 本质是有向无环图（DAG）。流程是静态编排好的，A 执行完必须执行 B。
* **Skill（动态决策）：** 是一种**目标驱动的动态路由**。Skill 中包含的是“目标”和“工具箱”。Agent 会根据当前的状态动态决定下一步调用什么工具，可以循环、可以回溯、可以跳过无用步骤。

## 3. Skill 的标准目录结构设计

一个工程化的 Skill 通常以**包（Package）**的形式存在，遵循“声明与实现分离”的原则。推荐的结构如下：

```text
skill_name/
├── metadata.yaml    # 注册表：定义 Skill 的名称、描述、触发意图（Intent）和依赖
├── prompt.md        # 大脑：Skill 的 System Prompt（角色设定、处理逻辑、SOP 流程）
├── tools/           # 手脚：可被 LLM 调用的原子化工具函数
│   ├── __init__.py
│   ├── fetch_log.py # 比如：获取日志的 Python 脚本，需包含强类型的接口注释
│   └── parse_ast.py
└── examples.md      # 记忆：Few-shot 示例，告诉 LLM 之前类似的问题是怎么解决的
```

## 4. 智能体的大脑：知识结构与决策机制

开发 Skill 必须理解 Agent 的“知识”从何而来。Agent 的能力由三部分组成：

1. **模型参数内化的知识（Parametric Knowledge）：**
   LLM 预训练得到的权重。它懂 Python 语法、懂 HTTP 协议、懂基础的排障逻辑。这部分**不需要**在 Skill 里重复教。
2. **上下文结构带来的环境激活知识（Contextual Knowledge）：**
   也就是你的 `prompt.md` 和 `tools` 注释。它将通用大模型“激活”并“收敛”到当前具体的业务场景中。它告诉大模型当前系统的 IP 是多少、数据库的表结构是怎样的。
3. **环境动作与反馈带来的动态决策参考（Dynamic/Episodic Knowledge）：**
   这引出了 **ReAct (Reason + Act)** 决策循环。Agent 的行动不是一步到位的，而是 `思考(Thought) -> 行动(Action) -> 观察反馈(Observation) -> 再思考` 的循环。运行时工具返回的真实报错或数据，构成了 Agent 解决当前问题的动态知识。

## 5. 核心架构：上下文按需加载与 Skill 激活逻辑

这是从“玩具 Agent”走向“工程化 Agent”的分水岭。

### 5.1 反面教材：一股脑塞入的“全量上下文”
早期我们在 IDE 里写代码，喜欢把整个项目的源文件全选、复制、粘贴给大模型。
* **痛点：** 污染了 Context Window，信噪比极低；大模型由于注意力机制（Attention）的限制，容易引发“幻觉”或“遗忘中间内容”；每次对话消耗大量 Token 成本。

### 5.2 最佳实践：基于 `agents.md` 的按需加载机制
在大型工程或复杂 Agent 中，我们引入**按需加载（Lazy Loading）**与**上下文分层**机制。

以 `agents.md`（或 `index.yaml`）作为整个工作空间的**路由字典（Manifesto）**。它的逻辑类似于操作系统加载内存：

1. **全局寻址（Intent Routing）：** Agent 启动时，上下文中只有极少数的全局 Prompt 和 `agents.md` 的摘要。当用户说“帮我排查一下订单服务的支付超时问题”，Agent 会先阅读摘要，决定：“我需要激活 `Skill_订单排障`”。
2. **按需加载（Context Swapping）：** 引擎动态将 `Skill_订单排障` 目录下的 `prompt.md`、特定的 `tools` 定义拉取并组装到当前的 Context Window 中。无关的代码和技能一律不加载。
3. **Skill 激活流程：**
   * **Load:** 加载业务 SOP（Prompt）+ 挂载可用工具链。
   * **ReAct:** 根据 SOP 步骤，开始 `Thought -> Action(调用工具排查) -> Observation`。
   * **Unload:** 任务解决，清理不需要的底层工具细节上下文，只保留最终的“排查结论”进入对话主内存。

这种逻辑不仅适用于排障，也同样适用于**利用 Agent 迭代优化项目代码**的场景（先让大模型看项目骨架/README，按需提取特定源文件进行修改，而非读取全量代码）。

## 6. 与 LLM 共舞：Skill 的生命周期与迭代沉淀

Skill 不是产品经理拍脑门写出来的，它是在对话中“长”出来的。

### 6.1 从对话到 Skill 的沉淀过程（0 -> 1）
1. **探索期（Chat-driven）：** 工程师在普通对话界面中，通过自然语言指挥 Agent 调用各种通用工具（如查数据库、调 curl）去解决某个新需求。
2. **提炼期（Prompt Engineering）：** 工程师发现某个解决路径非常有效，开始在对话中复盘：“刚才解决这个问题，我们先查了 A，再对比了 B，最后用 C 处理，请帮我把这个逻辑总结成一段标准的 Markdown SOP。”
3. **沉淀期（Solidification）：** 将总结出的 SOP 写入 `prompt.md`，把经常调用的散落工具封装进 `tools` 目录，并编写清晰的入参描述。打包发布，一个可复用的 Skill 就诞生了。

### 6.2 现有 Skill 的动态迭代（1 -> N）
当业务发生变化（例如订单服务改版），旧的 Skill 会在 ReAct 循环中频频遭遇 `Action Error`。此时，你甚至可以**用 Agent 来迭代 Skill 本身**：
* 用户告诉 Agent：“现在支付超时排障的逻辑变了，不需要查旧的 Redis 缓存，改查新的 ES 索引。”
* Agent 动态加载**该 Skill 自己的代码与 Prompt 上下文**。
* Agent 自主修改 `tools/fetch_log.py` 里的代码，并更新 `prompt.md` 里的 SOP。
* 保存生效。

## 7. 架构延伸：传统 Web 应用如何适配 Agent (Agent Observability)

我们开发了很多传统的 Web 应用 / 服务端程序，如何将它们的运行过程开放给智能体，方便 Agent 进行 Trace 追踪和需求迭代优化？

**核心理念：面向机器（Agent）的日志与追踪设计。**

传统应用的日志是给人看的（格式散乱、只有报错堆栈）。为了让 Agent 能够“看懂”应用的运行状态并据此优化，传统应用需要设计 **Agent-Friendly Trace Log**：

1. **语义化状态转移流（State Transition Logging）：**
   应用内部的关键流转需要输出结构化数据。例如：
   `{"event": "AUTH_FAILED", "module": "login_service", "reason": "token_expired", "user_context": {...}}`
   Agent 看到这样的 JSON Lines 甚至比看堆栈更容易理解业务痛点。
2. **暴露内部可观测性端点（Agent APM API）：**
   为 Agent 开发专用的 `GET /agent/trace/{trace_id}` 接口。当传统 Web 应用报错时，暴露给用户的不仅是错误信息，还要有一串 Trace ID。Agent 拿到 ID 后，通过该接口直接获取请求的全链路上下文（入参、数据库耗时、外部 API 响应）。
3. **基于反馈的闭环优化：**
   当 Agent 读取到上述格式化的运行时异常信息后，结合其“按需加载代码上下文”的能力，就能实现：`捕获传统应用报错 -> 分析结构化 Trace -> 定位源代码 -> 提出/实施修复方案`的自动迭代循环。

## 8. Skill 设计的最佳实践 (Best Practices)

1. **SRP（单一职责原则）依然适用：** 一个 Skill 只解决一个核心场景（如“代码 CR”、“特定服务查 log”）。不要试图写一个“解决一切后端问题”的上帝 Skill，大模型会因为注意力分散而表现糟糕。
2. **Fuzzy In, Structured Out（模糊输入，结构化输出）：** 工具函数（Tools）的输入可以依赖大模型根据上下文去推理提取，但工具函数返回给大模型的结果（Observation），**必须经过严格的清洗和格式化（例如截断超长无效字符串、转为紧凑的 JSON）**，否则极易撑爆 Context Window。
3. **防守型设计（Defensive Tooling）：** 在 Skill 赋予 Agent 写数据库、重启服务等高危权限时，必须在工具层做硬编码的拦截逻辑（如只能执行 `SELECT`），或者在工作流中强制加入 Human-in-the-loop（人工确认）节点。
4. **提供失败兜底（Fallback in SOP）：** 在 `prompt.md` 中写明：“如果工具 A 连续报错 3 次，请放弃尝试，转而使用工具 B，或者总结现有收集到的信息回复用户。” 防止 Agent 陷入死循环。

## 结语

从“写代码控制机器”到“写 Prompt+Tools 启发智能体解决问题”，这不仅是技术栈的迁移，更是工程师思维方式的升维。掌握好 Skill 的架构设计、上下文加载与 ReAct 协作机制，你就能在 AI 时代打造出真正的自动化基础设施。
